# 班集 · 代码审查报告（后端）

> 本目录记录对前后端 JavaScript 代码的**只读审查**结果。不含任何代码改动。
> 审查时间：2026-10-25 ｜ 范围：`student-backend/`（87 个 JS 文件 / 16492 行）
> 约定：每条给出「文件:行号 + 问题代码 + 量化影响 + 具体改法」，按严重度排序。

## 一、总体评价

**后端工程质量高于一般水平。** 具体体现在：

- **SQL 注入面已收敛**：88 处 `prepare()` 字符串拼接全部是表名/列名（SQL 标识符无法参数化），且**每个拼接点前都有白名单校验**（`READ_TABLES` / `WRITE_TABLES` / `JSON_WRITE_TABLES`），值一律走 `?` 占位符绑定。
- **缓存治理规范**：26 个 `Map` 中会影响增长的两个都做了淘汰——`connCache` 用 LRU（上限 10，超限关闭连接）、`bufCache` 按字节封顶 64MB 并有失效钩子。
- **事务边界正确**：多表写入、级联删除、跨表操作均包在 `db.transaction()` 内；`account.js` 甚至显式处理了「先换包裹再改密码」的顺序依赖。
- **事件循环意识明确**：`albumScan.js` / `albumThumbs.js` 注释里明确写了「不用 `fs.existsSync`——那是同步 IO，会阻塞事件循环（实测并发 16 张时…）」，并给出实测数据。
- **注释记录「为什么」而非「是什么」**：大量注释解释了设计动机与踩坑史（如 `app.js` 的 `deferredLoaders`、扫描子进程的 `expectExit` 标志）。

真正的问题集中在**少数几个"看起来对"的同步调用**上，而非结构性缺陷。

## 二、发现清单

### [中] bcrypt 同步调用阻塞事件循环

- **文件**：`student-backend/routes/account.js`（7 处）、`student-backend/routes/auth.js`（7 处）
- **代码**：

```js
// routes/auth.js:171
if (!unlockedByMnemonic && user.password && !bcrypt.compareSync(password, user.password)) {

// routes/auth.js:235
: bcrypt.hashSync(String(password), 10)

// routes/account.js:280
const hashed = bcrypt.hashSync(newPassword, 10);
```

- **问题**：bcrypt 是**故意设计得慢**的密码哈希算法（cost=10 即为抵抗暴力破解）。同步版本在 Node 主线程上跑，期间**整个后端的事件循环被完全阻塞**——所有并发请求（前端轮询、桌���小组件 IPC、缩略图批量请求）全部排队等待。
- **实测影响**（本机实测，Node v22.22.2）：

  | 调用 | 阻塞时长 |
  | --- | --- |
  | `bcrypt.hashSync(pw, 10)` | **64.6ms** |
  | `bcrypt.compareSync(pw, hash)` | **56.2ms** |
  | `bcrypt.hashSync(pw, 12)` | 225.9ms |

- **触发条件**：**登录、注册、改密码、切换加密模式**——都是用户高频且在意的操作。单账号场景下并发请求不多，体感主要是「登录时整个应用卡一下」（桌面小组件的心跳、正在进行的相册缩略图批量请求会一起停顿）。
- **建议改法**：改用异步 API。`bcryptjs` 自带 Promise 版本：

  ```js
  // 包装层（account.js:15 附近已有 useBcrypt 懒加载包装，沿用它）
  const hash = (pw) => new Promise((resolve, reject) =>
    useBcrypt().hash(pw, 10, (e, h) => e ? reject(e) : resolve(h)));
  const compare = (pw, h) => new Promise((resolve, reject) =>
    useBcrypt().compare(pw, h, (e, r) => e ? reject(e) : resolve(r)));
  ```

  逐处把 `await bcrypt.compareSync(...)` / `await bcrypt.hashSync(...)` 替换掉即可。
  **注意**：`account.js:267` 的 `compareSync` 位于 `||` 短路表达式中，改造时需先提取为 `const ok = await compare(...)` 再参与判断，勿破坏 `byMnemonic || byLocalRecover ||` 的短路语义。
- **风险**：低。纯机械替换，行为等价。改完需回归「登录 / 注册 / 改密码 / 退出隐私 / 明文库切换」五条路径。

### [低] 班干部职务树存在 N+1 查询

- **文件**：`student-backend/routes/cadres.js:20-34`（`buildTree`）、`routes/cadres.js:81`（防环检测）
- **代码**：

```js
function buildTree() {
  const all = allCadres();
  const membersStmt = db.prepare('SELECT id, cadre_id, student_id, student_name FROM cadre_members WHERE cadre_id = ? ORDER BY sort_order, id');
  const byId = new Map();
  all.forEach(c => byId.set(c.id, { ...c, children: [], members: membersStmt.all(c.id) }));
  ...
}
```

- **问题**：每个职务单独查一次成员表（N 个职务 = N+1 次查询）；`cadres.js:81` 的防环检测同样在 `while` 循环里逐级查父节点。
- **影响**：**有限**。班干部职务通常 10–20 个，即 10–20 次同步查询，better-sqlite3 下约 0.1–1ms，总计个位数毫秒。相比同文件里 `buildTree()` 被调用的频率（每次增删改职务都调），量级可接受。
- **建议改法**：可优化但不紧急。若要改，把成员表一次性全查后按 `cadre_id` 分组：

  ```js
  const allMembers = db.prepare('SELECT ... FROM cadre_members ORDER BY sort_order, id').all();
  const byCadre = new Map();
  for (const m of allMembers) {
    if (!byCadre.has(m.cadre_id)) byCadre.set(m.cadre_id, []);
    byCadre.get(m.cadre_id).push(m);
  }
  // 然后 all.forEach(c => byId.set(c.id, { ...c, children: [], members: byCadre.get(c.id) || [] }))
  ```

- **优先级判断**：**建议不动**。收益小、改动有回归风险，属于典型的"过度优化"。

### [低] 主题 store 的系统配色监听未解绑

- **文件**：`student-frontend/src/stores/theme.js:383`
- **代码**：

```js
darkMedia.addEventListener('change', onSystemModeChange)
```

- **问题**：`matchMedia` 的监听注册后没有对应的 `removeEventListener`。
- **影响**：**实际无影响**。Pinia store 是**模块级单例**，生命周期与整个应用一致，不存在「组件卸载后 store 还在监听」的重复注册问题。
- **建议改法**：**建议不动**。除非将来引入 store 的热重载/多实例场景，才需要补一个 `dispose()` 出口。

## 三、已排查且确认无问题的项

以下是本轮重点检查、**结论为健康**的方向，记录在案以免重复排查：

| 检查项 | 结论 |
| --- | --- |
| SQL 注入 | 表名/列名拼接点全部有白名单前置校验；值全部参数化绑定 |
| 缓存无上限增长 | `connCache` LRU 上限 10；`bufCache` 字节封顶 64MB + 失效钩子 |
| 事务原子性 | 多表写/级联删/跨表操作均已包 `db.transaction()` |
| 同步 IO | 56 处同步调用集中在启动期与一次性路径；运行期热路径已用内存索引规避（`albumThumbs`） |
| 正则回溯 | 未发现危险模式（均为简单量词，无嵌套量词） |
| 定时器泄漏 | 后端几乎无 `setInterval`；`sessions` / `usedNonces` 有 TTL 清理 |
| 事件监听解绑 | 前端 39 处卸载钩子；`App.vue` 全部监听均正确解绑或自移除 |
| 请求竞态 | `SearchDialog` 有丢弃机制；AI 流式用 `AbortController`；Dashboard 用 `pending` Promise 去重 |
| 响应式陷阱 | `watch` 多用 getter 形式，深度监听仅 5 处；无模板内联对象/数组 |
| 强制重排 | 157 处布局读取全在拖拽/测量场景（必要） |
| blob 泄漏 | `useThumbBatch` 有 objectURL `revoke` + `prune` 机制 |

## 四、优先处理建议

1. **bcrypt 异步化**（唯一有实际影响的项）——把 14 处同步调用改为 Promise 版，解除登录/改密时 60ms 级的事件循环阻塞。
2. 其余项**建议不动**。特别是 N+1 与监听解绑，属于"改了没收益、不改没风险"的类型，改动反而引入回归风险。
