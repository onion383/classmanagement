# 后端开发文档

本文件面向 `student-backend/`（Express 5 本地后端）。内容基于源码逐文件阅读整理，路由路径与导出名均以实际代码为准。

## 一、职责与运行方式

`student-backend` 是「班集」桌面应用的本地 HTTP 后端，由 Electron 主进程以子进程方式拉起，向本机前端（渲染窗口、桌面小组件、工具箱浮窗）提供全部业务数据接口。

- 启动方式：主进程 `electron/main.backend.js` 通过 `child_process.fork` 拉起入口 `student-backend/app.js`，工作目录为该目录本身。
  - 开发模式：使用系统 `node` 可执行文件 fork（探测结果缓存于 `userData/dev-node-path.txt`）。
  - 打包模式：`execPath` 指向 `process.execPath`（electron.exe）并注入 `ELECTRON_RUN_AS_NODE=1`，以 Electron 内置 Node 的「纯 Node 模式」运行，目标机无需安装 Node.js。
- 环境变量注入（由主进程 `electron/main.config.js` 提供）：`DATA_DIR`（数据目录，默认 `userData/data`）、`ALBUM_THUMBS_DIR`（相册缩略图缓存目录）、`SECURE_MASTER`（安全通道主密钥 K_master）、`DB_MASTER_KEY`（数据库静态加密主密钥，经 safeStorage/DPAPI 持久化）、`NODE_COMPILE_CACHE`。`execArgv` 固定带 `--expose-gc`（供性能面板手动 GC）。
- 监听端口：`app.js` 读取 `process.env.PORT`，未设置时默认 `3000`；主进程 fork 时不注入 `PORT`，故正常运行端口为 3000。服务仅绑定回环地址 `127.0.0.1`，不监听 `0.0.0.0`，避免触发 Windows 防火墙弹窗。
- 进程模型与主进程契约：
  - 就绪上报：`app.listen` 回调内 `process.send({ type: 'backend-ready', port })`，主进程据此置位就绪并广播给渲染窗口。
  - 心跳：主进程周期性发送 `{ type: 'ping' }`，后端仅在不阻塞时回 `{ type: 'pong' }`；超时（疑似假死）触发主进程重连。
  - 性能面板：响应 `mem-query`（回 `mem-report`，`process.memoryUsage()`）与 `gc-request`（回 `gc-report`）。
  - 端口占用自动重试：`EADDRINUSE` 时 1 秒后关闭并重听；其余监听错误退出进程。
- 启动日志：主进程将子进程 stdout/stderr 落盘至 `userData/data/backend.log`。

## 四、关键机制

### 4.1 启动与初始化流程（app.js / init.js）

1. `app.js` 顶部先做严格依赖收敛：`require('./db')` → `require('./dbManager')`（此处会解析 `DB_MASTER_KEY`，缺失即抛错）与 `services/secureChannel`（读取 `SECURE_MASTER` 决定是否启用加密），并立即加载登录必需的路由 `routes/auth`、`routes/account`。
2. 中间件顺序：`cors()` → Host 校验（仅放行 `localhost/127.0.0.1/[::1]`，否则 403）→ `express.json({ limit: '200mb' })`（备份包可能数十 MB）→ 安全通道 `requestDecrypt` + `responseEncrypt`（仅当 `secureChannel.hasMaster()`）→ `/api/secure/handshake` 公开端点。
3. 静态资源鉴权：`/uploads` 与 `/api/background` 分别经 `authStatic()` 后托管 `dbManager.uploadsDir`、`dbManager.backgroundDir`。
4. 路由挂载分两批：
   - 关键路由（登录即可用）：`/api`→auth、`/api/account`→account、`/api/students`→`createDynamicTableRouter('students', { minCount:1, protectedColumns:['学号','姓名'] })`；随后托管生产前端静态文件 `../dist`。
   - 非关键路由（懒加载）：`startServer` 的 `listen` 回调内，用 `setImmediate` 逐个 `require` 并挂载 `/api/schedule`、`/seats`、`/leaves`、`/album`、`/group-manage`、`/scores`、`/duty`、`/widget-settings`、`/undo`、`/activities`、`/countdowns`、`/cadres`、`/ai`，以及含 multer 的 `/api/fee-records`（学生表/班费表的动态表工厂，班费表另挂 `POST /upload-receipt`）。懒加载目的是把 sharp/pdf-parse 等重依赖的加载成本推迟到就绪信号之后。
5. 监听回环地址并上报：`app.listen(port, '127.0.0.1')` 成功后 `process.send({ type:'backend-ready', port })`；随后 `setImmediate` 调用 `dbManager.warmup()` 后台暖机（提前打开 `index.db`，消化一次冷启动成本）。
6. `init.js` **不是**启动初始化脚本，而是一个独立小工具：导出 `mapType(sqlType)`，用于把 SQL 类型名映射为前端中文类型名（整数/小数/日期/文字）。真正的库初始化在 `schema.js` 的 `initSchema`。

### 4.2 数据库（加密 SQLite / 多库管理）

- 驱动：`better-sqlite3-multiple-ciphers`（SQLCipher 兼容，支持 `PRAGMA key`），在 `dbManager` 中懒加载原生模块，缩短就绪时间。
- 库文件位置：均在 `DATA_DIR`（默认 `userData/data`，可用 `app-config.json` 覆盖）下。
  - `index.db`：主密钥加密的**登记表**（registry：slug/username/wrapped_key/encrypted/created_at）。
  - `${slug}.db`：每个班主任一个**自含加密库**（业务数据 + 应用设置 + users 账号同行）。slug 形如 `@` + 12 位十六进制。
  - `data/.jwt-secret`：JWT 兜底密钥文件；`data/db-master.key`：DB 主密钥密文（由主进程写入）；`album-thumbs/`、`album-trash/`：缩略图与相册回收站。
- 密钥体系：
  - 主密钥 `DB_MASTER_KEY`（环境变量注入，`.env` 已移除明文）经 `sha256` 派生 `WRAP_KEY`，用于 AES-256-GCM 包裹/解包各库随机生成的 32 字节库密钥（`wrapKey`/`unwrapKey`）。
  - 便携备份另用「用户密码/助记词」派生钥匙包裹库密钥（`wrapKeyBySecret`/`decryptBundleKey`），使备份包不依赖服务端主密钥。
  - 明文库（`encrypted=0`）不下发 `PRAGMA key`，registry 中 `wrapped_key` 以空串占位。
- `db.js` 的 `db` 是一个 **Proxy**：`db.prepare/exec/transaction` 等访问转发到「当前请求绑定的库连接」(`dbManager.current()`)，因此各路由沿用 `require('../db').db.prepare(...)` 即自动命中登录者库。
- 请求绑定：`middleware/auth` 校验 JWT 后取 `user.dbSlug`，调用 `dbManager.withDb(slug, () => next())` 通过 `AsyncLocalStorage` 绑定；未绑定库的请求会被 `current()` 抛「未绑定数据库连接」拒绝。
- 连接缓存：`connCache` 按 slug 缓存已打开连接，上限 `CONN_CACHE_MAX = 10`，超出按 LRU 关闭驱逐（`touchConn`/`setCachedConn`/`evictConn`）。
- 性能 PRAGMA：`busy_timeout=5000`、`journal_mode=WAL`、`synchronous=NORMAL`、`cache_size=-20000`、`temp_store=MEMORY`。
- schema 与迁移：`schema.js` 的 `initSchema(conn)` 对所有表用 `CREATE TABLE IF NOT EXISTS`，并以「查 `PRAGMA table_info` 后按需 `ALTER TABLE ADD COLUMN`」的方式对存量库做列迁移（如 widget_settings 的 `desktop_apps/class_info`、album_photos 的 `thumb_path`、groups 的 `gender`、cadres 系列等）；另有 `ensureTableWithMigration` 处理表级迁移。索引以 `CREATE INDEX IF NOT EXISTS` 幂等创建。每次打开某库连接（`getConn`）都会调用 `initSchema`，故迁移对存量库自动生效。
- 加密方式就地切换：`convertDbEncryption(slug, encrypt, onProgress)` 严格按「关闭连接 → 退出 WAL → 预检完整性 → 备份 → rekey → 转换后校验 → 回写登记 → 删备份」执行，任一步失败从备份回滚，绝不留下中间态；由 `routes/account.js` 的 `POST /db-encryption` 以 NDJSON 流上报步骤级进度。

### 4.3 鉴权（JWT 中间件）

- 密钥：优先 `process.env.JWT_SECRET`（≥16 字符），否则读取 `DATA_DIR/.jwt-secret`，不存在则随机生成并持久化（兼容迁移旧位置 `student-backend/.jwt-secret`）。导出的 `SECRET` 供登录/注册签发复用。
- Token 解析顺序（`resolveToken`）：`Authorization: Bearer` 头 → `Cookie: token=` → URL 查询参数 `token`（供 `<img>`/CSS `url()` 等无法带头部的资源使用）。
- `auth(requiredRoles)`：无 Token 返回 401；校验通过后按 `requiredRoles` 校验 `user.role`（不匹配 403）；随后 `dbManager.withDb(user.dbSlug || 'default', next)` 绑定库。业务接口普遍使用 `auth(['teacher'])`。
- `authStatic()`：仅校验 Token 有效性、不区分角色，用于 `/uploads` 与 `/api/background` 静态资源。
- 令牌载荷：`{ userId, username, role, dbSlug }`，有效期 7 天（登录/注册处 `expiresIn: '7d'`）；登录成功同时写 `token` Cookie（httpOnly、sameSite=lax）。

### 4.4 安全通道（secureChannel ↔ 前端 setupSecureAxios）

- 启用条件：仅当主进程注入 `SECURE_MASTER`（64 位 hex，32 字节）时，`app.js` 才安装 `requestDecrypt`/`responseEncrypt`。未注入时各函数安全降级为明文直通（`hasMaster()===false`）。
- 握手：前端 `POST /api/secure/handshake` 提交其会话临时公钥，后端 `performHandshake(clientPubB64)` 生成后端 P-256 临时密钥对，ECDH 求共享密，再以 `HKDF-SHA256(ikm=共享密, salt=K_master, info='campus-secure-v1', 32)` 派生会话密钥，返回 `{ sessionId, pub }`。会话存于内存 `sessions`，TTL 15 分钟（`SESSION_TTL_MS`）。
- 数据面：请求体形如 `{ session, d }`（`d = base64(iv).base64(tag).base64(ciphertext)`），`requestDecrypt` 解密后写回 `req.body` 并记 `req.sessionId`；`responseEncrypt` 包装 `res.json`，仅对加密会话的纯 JSON 数据回包 `{ d: seal(...) }`。豁免路径前缀：`/api/secure`、`/uploads`、`/api/background`。
- 策略透明：请求非密文则明文放行；仅收到过加密请求（`req.sessionId` 已置位）的会话才回包加密，前端开关与后端不一致时各自退化为明文，不破坏功能。
- 与前端对应：`student-frontend/src/composables/secureAxios.js` 的 `setupSecureAxios(axios)` 负责客户端一侧——请求拦截器对 JSON 请求体加密（FormData/GET 直通），响应拦截器检测 `{ d: '...' }` 自动解密，解密失败视为会话过期，`clearSession()` 后重新握手重试一次；错误响应同样尝试解密以读取 `error`/`needConfirm` 等字段。加密原语在 `student-frontend/src/composables/secureChannel.js`（`safe`/`encryptBody`/`decryptBody`/`clearSession`），与后端 HKDF/AES-GCM 参数一一对应。

### 4.5 数据恢复密钥（recoveryKey）

- `POOL` 为约 512 个常见汉字；`pickPhrase()` 用 `crypto.randomInt` 随机取 12 字组成恢复密钥（连续字符串）。
- `deriveRestoreHash(phrase)` = `sha256('restore:' + phrase)` 十六进制；服务端只存哈希（`users.recovery_hash`），不存明文。
- `normalizePhrase(phrase)` 仅保留汉字，兼容用户粘贴带序号（`1.水`）或空格的格式；`formatPhrase` 生成带序号的展示串；`safeEqualHash` 做定长缓冲区的常数时间比较。
- 使用方：注册（有密码账号先生成草稿、抄写前 3 词确认后建库，见 `routes/auth.js`）、重置恢复密钥（`routes/account.js` `GET /recovery-key`）、忘记密码（`POST /api/recover-password`）。`dbManager.decryptBundleKey` 在解密助记词包裹的备份钥匙时也复用 `normalizePhrase`。

### 4.6 表格服务（tableService）

- 定位：学生表与班费表共用的「动态列」表格逻辑，`routes/dynamicTable.js` 的工厂将其包成 REST 路由。
- 关键能力：`queryAll`（按 position 排序，字段元数据缺失时降级用结果键）、`insertRow`/`updateRow`/`deleteRow`（支持 `atPosition` 插入、`minCount` 最少保留）、`moveRow`、`reorderRows`、`addColumn`/`deleteColumn`/`moveColumn`/`renameColumn`（列元数据存 `table_meta`，`sort_order` 维护顺序）、`importRows`（自动补建缺失列并批量事务插入）。
- 安全约束：列名白名单正则 `^[a-zA-Z0-9_\u4e00-\u9fa5]+$`，保留字段 `id/position/atPosition` 禁止直接操作；`protectedColumns` 由调用方传入（学生表保护 `学号/姓名`），删除列时至少保留一个数据字段。

### 4.7 文件与媒体处理

- multer 上传：
  - 班费收据：在 `app.js` 懒加载块内配置，`diskStorage` 落盘到 `dbManager.uploadsDir`，限制单文件 10MB、仅图片（jpg/png/gif/webp/bmp，扩展名 + MIME 双校验），并在 `POST /api/fee-records/upload-receipt` 做**图片魔数校验**（读取真实字节签名，非图片即清理并拒绝）。
  - AI 附件：`routes/ai.upload.js` 用 `multer({ dest: os.tmpdir()/ai-uploads })` 临时存储，解析后删除。
- sharp 缩略图：`routes/album.js` 的 `genThumb` 懒加载 sharp，对图片 `rotate()`（处理 EXIF 方向）后 `resize(512,512,{fit:'inside'})` 输出 512px JPEG（q82），缓存到 `dbManager.thumbsDir`（**按库隔离的子目录 `{thumbsDir}/{slug}/{photoId}.jpg`**，见 `albumThumbs.js`）。有全局并发信号量，最多同时 **4** 个缩略图任务（实测 16 核机器上并发 4 最优：单张 20.2ms，并发 8 回退到 24.7ms）。临时文件必须仍以 `.jpg` 结尾（ffmpeg 靠扩展名推断封装格式，否则视频封面全部生成失败）。
- **缩略图按库隔离（2026-10-22 修多租户串图）**：各班主任库的 `album_photos.id` 都从 1 开始独立自增，而缩略图文件原本固定命名 `{photoId}.jpg` 且**所有库共用同一个 `thumbsDir`** —— 库 A 的 id=1 与库 B 的 id=1 指向同一个文件，后扫描的库覆盖先扫描的库，切换账号重登旧账号会看到别人的照片（实测复现：库A 红图/库B 蓝图各自 id=1，最终两边都读到蓝色）。现改为 `albumThumbs.thumbPathFor(slug, photoId)` 按 slug 分目录，各库互不干扰。`dbManager.currentSlug()` 取当前请求绑定的库标识（`withDb` 写入 ALS 上下文）；后台扫描任务在函数开头显式捕获一次 slug（不依赖 ALS 在异步链里的传播）。
- **缩略图内存缓存（2026-10-22 性能优化）**：`albumThumbs.js` 维护两块内存缓存——① 索引 `photoId → {path, v}`（兼作「文件存在」的判据，替代 `fs.existsSync`）；② 文件内容的 LRU 缓存（按**字节数**封顶 64MB，非按条数）。实测每张缩略图的查找成本：`fs.existsSync` 100~524us（**同步 IO，阻塞事件循环**，并发 16 张时 5ms 定时器延迟 p95 达 9.7ms）、磁盘读 2402us、DB `prepare+get` 226us → 全部命中内存后单请求 1829us → 167us（约 11x）。缓存失效点：删照片/删相册 → `forgetPhoto`/`forgetAlbum`；重新生成 → `rememberThumb` 覆盖；`THUMB_VERSION` 变更 → 版本不匹配的条目视为无效，读取时自动重建。**`/photo/:id/thumb` 已不再使用 `fs.existsSync`**（改异步读，读不到即重建）。
- **批量缩略图接口（2026-10-22）**：`POST /api/album/photo/thumbs`，请求体 `{ ids: [photoId,...] }`（上限 200），响应为二进制——**每张图「4 字节小端长度 + JPEG 数据」逐张拼接**（不是头部长度表，便于前端流式解析），响应头 `X-Thumb-Ids` 给出实际返回的 photoId 顺序。缺图默认**现场生成**（与单张接口同一套 `genThumb` 逻辑），否则新扫描进来的照片 `thumb_v=0` 会让批量全部落空；**但现场生成要过配额闸**（见下方「扫描的低干扰约定」，过不了就转需求队列，本次直接跳过）。批量按「已有缓存的先返回、缺图的另算」两阶段处理 —— 配额闸只看**缺图数**，否则一个 200 张的请求会因为其中 180 张已缓存被误拒。不做截断式处理（只生成前 N 张、其余排队）：那会让同一屏里靠前的格子有图、靠后的没有，比全都没有更难解释。实测批量 0.22~0.32 ms/张 vs 逐个并发 6 的 2.15 ms/张（约 10x）。前端解析在 `utils/albumMedia.js` 的 `parseThumbBatch`，预取逻辑在 `composables/useThumbBatch.js`；批量没拿到的格子回落到单张 `/thumb` 接口。**注意 better-sqlite3 不支持 `IN (?)` 的展开参数，必须用问号占位逐个绑定**。
- ffmpeg 视频封面：视频用 `services/ffmpeg.js` 定位的 LGPL 版 ffmpeg 命令行抓第 0.1 秒帧并缩放为 512px 宽。构建须保留 x86asm（nasm 汇编路径），勿在 `resources/ffmpeg/build.sh` 里加 `--disable-x86asm`：那会让 scale 滤镜的插值核落回被 GCC 8.1 编坏的 C 实现，封面输出花屏（2026-10-22 实测，详见 build.sh「裁剪警告」与 BUILD-INFO.txt 修订记录）。
- 缩略图缓存版本：`albums_photos.thumb_v` 记录生成时的 `THUMB_VERSION`（`routes/album.js` 常量）。`/photo/:id/thumb` 发现 `thumb_v < THUMB_VERSION` 会现场按新参数重建并回写；改尺寸/质量时把后端 `THUMB_VERSION` 与前端 `utils/albumMedia.js` 的 `ALBUM_THUMB_VERSION` **同时 +1**（前端版本拼进 URL 的 `?v=`，否则浏览器会按 max-age 继续用旧图一天）。
- pdf 解析：`routes/ai.upload.js` 上传 `.pdf` 时先 `require('../services/pdfDomShim')` 安装纯 JS DOMMatrix 全局（替代 35MB 的 @napi-rs/canvas），再用 `pdf-parse` 的 `PDFParse` 类做文本提取，用完 `destroy()`。
- mammoth：`.docx/.doc` 用 mammoth `extractRawText` 提取文本。
- xlsx：`.xlsx/.xls` 用 `xlsx` 读取每个 Sheet 并转为制表符文本；`.txt/.csv/.md/.json/.xml/.html` 直接按 UTF-8 读取。提取文本超过 100000 字符截断。
- **索引绝不能凭空清空（2026-10-22 数据丢失级修复）**：`fullScan` 原先「开头删光旧索引 → 再收集磁盘清单」，收集阶段一被停止/暂停/子进程被杀就直接 `return`，索引已空而新索引一条没写 → **文件夹里照片一张没少、相册却变 0 张**。现改为「先收齐清单 → 处理文件 → 最后只删清单外的行」，任何中断点上索引都只是旧数据。另有一条同源路径：`walkMediaFiles` 里 `readdir` 失败只 `catch { continue }`（权限、OneDrive 占位未落地、网络盘抖动），残缺清单会让末尾「清理已删除文件」把读不到的那整片目录误删干净。现 `collectMediaFiles` 返回 `{ files, complete }`（`complete=false` 表示有目录读不到，不再静默吞掉），**清理步骤的前置条件是 `task.scanned >= files.length` 且 `complete`**，任一不满足就整段跳过清理；承担删除的 `deletePhotosNotIn` 在 `trust=false` 时一行都不删。因为不再删光，`fullScan` 必须显式刷新已有行（`updateMeta` + **无条件重建缩略图**），否则「全量更新」会退化成增量。
- 相册后台扫描：`albumScan.js` 的 `walkMediaFiles` 递归读取相册绑定文件夹**及其所有子文件夹**里的图片/视频（显式栈遍历，2026-10-22 起由「只扫根目录一层、子文件夹单独建相册」改为递归；symlink/junction 目录 `isDirectory()` 为 false 不跟进、天然无环；`collectMediaFiles` 先收清单再处理、边收边累计 `task.total`）。扫描体整体 `try/finally` 保证任务在取消/抛错时都被摘掉（否则 `/status` 永远报 `scanning:true`、前端轮询结束不了）。此前按旧规则清理过的子目录照片，下次扫描会作为新增文件重新进索引。在跑任务有两份视图：**主进程内存态** `scanWorker.active`（`GET /api/album/tasks` 遍历它，含 `mode`/`paused`/`scanned`/`total`，软件自己发起的扫描 —— 新建相册后的首次全量、undo/redo 触发的重扫、「刷新」按钮 —— 与用户点按钮发起的在前端「任务管理」里一视同仁；子进程崩了或主进程重启都会清空，所以不会把「上次残留的断点」误报成「正在扫描」）与**库表态** `album_scan_tasks`（跨进程真源，`/tasks/pending` 读它）。删除照片走 `albumOps.moveToTrash`（应用内回收站，跨设备 EXDEV 时退化为复制+删除）。
- **拍摄时间改用 EXIF（2026-10-22）**：时间轴原先按 `album_photos.mtime`（文件修改时间）分组，但 mtime 会被复制、解压、聊天软件转存、同步盘上传下载**全部改写** —— 一批 2019 年拍的照片导出来就全变成「今天」。现由新模块 `albumExif.js` 解析图片自带的 EXIF 拍摄时间，取值优先级 `DateTimeOriginal(0x9003)` → `DateTimeDigitized(0x9004)` → IFD0 `DateTime(0x0132)`，都取不到再从 XMP 里正则捞 `exif:DateTimeOriginal`，**仍读不到就是读不到 —— 不拿 mtime 兜底**（用户明确要求）。**自己解 TIFF/IFD 而不引第三方 exif 库**：只需要三个 ASCII 标签，约 80 行，比多一个依赖更可控。三个坑：① EXIF 块内所有偏移都相对 TIFF 头，带 `Exif\0\0` 前缀时 IFD0 偏移与数据偏移都要加 base（漏加会导致带前缀的 JPEG 全解析失败）；② 相机没上电会写 `0000:00:00`、时钟没校准会写未来时间，故 `MIN_YEAR=1980` + 「比现在晚 2 天以上」一律判非法；③ 读不到时 `readExifDate` 吞掉异常返回 `''`，绝不让单张坏图中断整个扫描。视频无 EXIF（ffprobe 要起子进程，扫描时每张都调不划算）一律归「未知时间」。
  - **为什么不用 mtime兜底**：文件时间不是拍摄时间，拿它冒充等于凭空造一个假日期，比「未知」更坏 —— 用户会把假日期当真日期去认照片。所以读不到时 `photo_date` 留空串，前端归到时间轴**最底部**的「未知时间」分组（导出索引里同样排最后）。
  - 新增两列（`schema/schema.album.js` 幂等 `ALTER TABLE`）：`exif_date`（EXIF 原始拍摄时间）与 `date_src`（`'exif'`/`'none'`，老库默认空串 = 还没核过；用 `'none'` 而非空串表示「已核过但没读到」，好让增量扫描区分「要重读」与「读过确实没有」）。`resolvePhotoDate(filePath, mtime, isVideo)` 是唯一入口，返回 `{date, exif, src}` 供两条扫描路径共用。
  - **存量库自动纠正**：`incrementalScan` 的跳过条件从「mtime 相同就跳过」放宽为「mtime 相同**且** `date_src` 不是 `''`/`'mtime'` 才跳过」，所以老库的行（以及早期用 mtime 兜底写下的 `'mtime'` 行）会在下次「刷新」时补读一次 EXIF 把日期改回来；此时**只更新日期不重建缩略图**（图没变，重建是白费 CPU）。`date_src` 有值的行不再重复读盘。
  - `GET /api/album/:id/photos` 的排序键从 `mtime DESC` 改为 `photo_date DESC, mtime DESC, id DESC`（否则分组顺序会随「文件被转存过几次」而变），配套加索引 `idx_album_photos_album_date (album_id, photo_date DESC)`。**空串在 SQLite 里小于任何非空字符串，DESC 排序天然落到最后**，所以「未知时间」组自动在最底部，不需要额外的排序表达式。
  - **新列必须跟着走**：虚拟相册复制（`createVirtualAlbum` / 合并）、`photos/move`、undo/redo（`undo.executors.js` 的 4 处 INSERT + 前端登记的撤销载荷 `AlbumManageDialog` / `AlbumView`）全部要带上 `exif_date`/`date_src`，否则照片一被移动/撤销还原就退回「只有 mtime」的状态。
- **虚拟相册也要能刷新（2026-10-22 新增第三条扫描模式）**：虚拟相册的索引是**从别的相册拷贝**来的，所以同样会过期 —— 拷来的是拷贝那一刻的 `photo_date`（源相册后来补读了 EXIF 它不会跟上）、`THUMB_VERSION` 升了缩略图也不重建、用户手动移入的照片更是只有路径没有缩略图。而它 `folder_path` 为空、没有目录可遍历，所以 `fullScan`/`incrementalScan` 都在入口直接 return，等于永远不更新。现新增 `albumScan.refreshVirtual`（`mode='virtual'`），**只按已有索引行刷新**：不遍历磁盘、不新增行、不删除行，逐行把 `file_name`/`file_size`/`mtime` 与拍摄时间、缺失或过期的缩略图补齐。三条关键约定：
  - **源文件不存在时只跳过、不删行**。虚拟相册的索引是拷贝来的，文件是否还在由**源相册**的扫描判断；在这里删行会导致「源相册挪走文件 = 虚拟相册凭空丢照片」。
  - **断点用行 id 而非文件路径**（`done_path` 存 `String(cursor)`）。索引行主键稳定，路径可能因文件被移动而变。
  - **幂等**：三项判据（`metaChanged` / `needDate` / `needThumb`）全不成立就不 stat 之外读盘、不写库，重复点刷新不会白跑全表。`needDate` 覆盖 `date_src` 为空（没核过）与 `==='mtime'`（早期兜底值）。
  - 分派链路：`routes/album.js` 的 `dispatchVirtual()` → `scanWorker.dispatchScan(..., 'virtual', ...)` → `worker.scan.js` 的 `runScan` 按 mode 分派。`POST /:id/rescan` 改为**按 `album.kind` 自动分流**（虚拟 → virtual 模式并返回「已开始更新虚拟相册的照片信息与缩略图」），前端不用传 mode；续扫路由 `/tasks/resume` 也放行 virtual（并校验 mode 与 kind 一致，不一致就丢弃断点）。
  - 前端：`AlbumView.vue` 的「刷新」按钮原先对虚拟相册是 **disabled** 的，现已放开，提示文案改为「按已有索引更新拍摄时间与缩略图（不遍历文件夹）」。
  - **踩到的坑**：`waitWhilePaused` 查 `album_scan_tasks` 查不到行时**当作任务被取消**（`task.cancelled=true; return false`），所以直接调 `refreshVirtual` 而不先 `claimScanTask` 会第一轮就静默退出、看起来「什么都没做」。生产路径上 `dispatchScan` 总是先 claim 再派活，正常不会遇到；写单测时必须自己补 `claimScanTask`。
  - 回归用例 `testjs/units/refresh-virtual.test.js`（9 项，含幂等/不删行/文件夹相册误调直接返回/断点续刷）。
- 两种相册（`albums.kind`）：`folder` 绑定文件夹、由扫描生成索引；`virtual` 不绑定文件夹、索引由 `createVirtualAlbum` 从别的相册复制而来（`INSERT OR IGNORE` 同册去重），**全程只写 `album_photos`，绝不移动/删除磁盘文件**。语义：来源是 `folder` 相册时源侧索引不动；来源是 `virtual` 相册时把源行删掉（一个增加一个减少）并清掉它已经没人引用的缩略图。复制出来的行 `thumb_path` 置空，缩略图由 `/thumb` 按新 id 现场生成，避免两个相册共用同一个缩略图文件。虚拟相册的 `POST /:id/rescan` 返回 400，`fullScan`/`incrementalScan` 入口也有兜底 return。
- 移动照片索引 `POST /api/album/photos/move`（body `{ photo_ids, target_album_id }`）：与 `createVirtualAlbum` 同一套语义，只写 `album_photos`。目标必须是 `virtual`（`folder` 相册数量必须等于磁盘目录里的文件数，故 400 拒绝）；来源是 `virtual` 时删源行（一个减少一个增加），来源是 `folder` 时源行不动（数量仍与文件夹一致）；目标已存在同一 `file_path` 时 `INSERT OR IGNORE` 不重复插入，所选照片本来就在目标相册的直接跳过。新行 `thumb_path` 同样置空。返回值带 `photos` 明细（`source_photo_id` / `source_album_id` / `inserted` / `source_removed` 等），供前端登记 `album_photo_move` 撤销记录。
- **扫描的低干扰约定（2026-10-22，已升级为「独立子进程」）**：扫描是浮动任务（接口立刻返回「已开始」）。最初与其他接口同进程，靠「长事务分批 + 现场生成走配额闸」两条规矩把干扰压下去，实测事件循环延迟 p95 从秒级降到 15ms。但残余风险仍在：sharp 与请求路径**共用 libuv 线程池**（默认 4，恰好等于 `MAX_CONCURRENT_THUMBS`），扫描批量出图照样会占满它。现在扫描整体搬进**独立子进程**，主进程只跑 HTTP 接口与「零星几张」的补图：
  - **为什么必须是独立进程而不是 worker_threads**：libuv 线程池是**进程级全局静态**，所有 Worker 共用同一个池子；`worker_threads` 只能隔离 V8 堆与 JS CPU，而 sharp 的解码/重采样全在原生线程池上。只有 fork 出的独立进程才有自己的线程池。
  - **分工**（用户拍板）：主进程 `routes/album.js` 只在缺图数 ≤ `ON_DEMAND_LIMIT = 8`（**全局在途量**：在途 + 已转交子进程待生成）时现场生成；超出的 id 经 `scanWorker.forwardDemand()` 丢给子进程的 demand 队列（`DEMAND_BATCH = 8` 串行消化）。补图与**写库都在子进程做**，主进程不碰这些行的写；子进程出图后通过 `thumbs` 回报让主进程预热内存索引（省掉首屏那次异步读盘，约 10 倍差距）。
  - **配额闸的僵尸 id**：`pendingInChild` 用 Map 记「转交时刻」而非裸 Set —— 子进程补图**可能失败**（源文件被删、文件损坏），失败的 id 永远不会出现在回报的 `thumbs` 列表里。若无过期机制，它会永久留在集合里，而配额闸把 `pendingInChild.size` 算在内，于是攒够 8 个之后主进程再也不肯现场生成任何图，**所有缩略图请求恒 404（功能被锁死）**。故设 `PENDING_TTL_MS = 60000`，`claimOnDemand()` 入口先 `sweepPendingInChild()`；另有 2000 条的兜底上限。
  - **保留的进程内规矩**（依然有效）：`DELETE_BATCH = 2000` 分批删 + 批间 `await yieldLoop()`（`setImmediate`）；文件循环每 `SCAN_YIELD_EVERY = 16` 个文件让出一次。**注意理由不是「解锁读」** —— WAL 下读写不互斥（实测大事务 DELETE 期间另一连接读 p95 仅 4.9ms），真正被切碎的是 **better-sqlite3 同步执行导致整个 Node 进程无法响应任何请求**。
  - **生命周期**：懒启动（第一个扫描请求才 fork，不跟软件启动抢 CPU/IO）；最后一次派活后空闲 `SCAN_WORKER_IDLE_MS = 60000` 发 shutdown 让它退出；崩溃后延迟 1200ms 重建，每分钟最多 6 次。`app.js` 在 `process.on('exit')` 里调 `scanWorker.shutdown()` —— 父进程退出后 fork 出的子进程**会继续活着**（Windows 上更是彻底没人管），变成一个孤儿进程继续扫库写库，而前端已显示「后端已关闭」。
  - **`expectExit` 标志**：主动 shutdown 走 `child.kill()` 时，Windows 上 exit 回调拿到的是 `code=null + signal='SIGTERM'`，与崩溃一模一样。少了这个标志会被当成崩溃去 `scheduleRestart()`，而主进程正要退出时，重建出来的 worker 没人管，就成了永不退出的孤儿进程。另：exit 回调先比对 `child !== proc`，避免 shutdown 后又派活建了新 child 时被旧进程的退出回调把状态清空。
  - **`scanWorker.killNow()`**：立刻 kill 走崩溃路径（不发 shutdown），用于「模拟进程被杀」与紧急止损 —— 库表里的断点记录会留下来，可供 `/tasks/resume` 续扫。
- 暂停：`POST /api/album/:id/pause` 走 `scanWorker.requestPause`：主进程写库 `state='paused'` 并发 IPC，子进程在检查点由 `waitWhilePaused(conn, task, albumId)` 挂短定时器原地等（本地 `task.paused` 标志优先命中，库表按 `STATE_CHECK_INTERVAL = 300ms` 节流兜底）。暂停期间任务仍在库表里（`/status` 仍返回 `scanning:true` + `paused:true`），所以前端那一行不会消失、可随时继续；「停止」优先于暂停（stop 会同时把 `paused` 清掉）。
- 相册封面：`readAlbums()`（`GET /api/album` 与 `/api/dashboard` 共用）在列表查询里额外带出 `cover_photo_id`——按 `mtime DESC, id DESC` 取该册**第一张非视频**照片的 id（`NOT_VIDEO_SQL` 用 `LOWER(file_name) NOT LIKE '%.mp4'` 等排除，扩展名需与 `mediaTypeOf` 的 `VIDEO_EXT` 保持一致）。前端相册卡片直接用 `/api/album/photo/{cover_photo_id}/thumb` 当封面，不必把整册照片拉回来过滤。
- **扫描任务持久化 + 断点续扫（2026-10-22）**：软件被关掉/崩溃时，正在跑的相册扫描会丢，大相册下次要从头再来（缩略图全部重生成）。现把「进行中的扫描」落到库表 `album_scan_tasks`（`schema/schema.album.js` 幂等建表）：`album_id` 主键、`mode`（full/incremental）、`phase`（collect/process）、`done_path`（**断点：已处理完的最后一个文件路径**）、`scanned`/`total`、`state`（running/paused/cancelled，**只有主进程写**）、`token`（**本次扫描的归属标识**，见下方「跨进程状态同步」）、`started_at`/`updated_at`。
  - **断点用文件路径而不是序号**：重启后目录内容可能变化（文件被增删），序号会错位，路径能稳定定位。续扫时重新收集清单，定位到 `done_path` 的位置、从它的**下一个**继续。
  - **写入时机**：见下方「跨进程状态同步」—— 派活的瞬间由**主进程**写好这一行；子进程每处理完一个文件推进断点（`PERSIST_EVERY = 20` 批量写，1 万张不必写 1 万次库，崩溃时最多重扫一批）；扫描**正常跑完**（`persistScanClear`）或**用户主动点停止**时清除记录（这两种情况不需要续扫；用户主动停止 = 明确放弃，下次不该再续起来）；进程被杀/异常退出时记录留存，供下次续扫。
  - **跨进程状态同步（token + state 独占写，2026-10-22）**：库表 `album_scan_tasks` 是**唯一真源**，IPC 只承载「派活/报活」。两条铁律：
    - **`state` 由主进程独占写，子进程一律不写**。若子进程在启动时无条件写 `state='running'`，会把用户刚点的「停止」抹掉 —— 扫描照跑，用户以为停了其实没停。曾试过用 `CASE WHEN state='cancelled' THEN ... ` 保住，但会与「停止后重新扫描」冲突（新扫描也被立刻取消），故改为由主进程在派活瞬间 `claimScanTask()` 写好 `state=running`，子进程只推进断点。
    - **`token` 标识「本次扫描的归属」**（每次派活 `Date.now()*1000 + 递增序号`），所有推进断点的 `UPDATE`/收尾的 `DELETE` 都带 `WHERE album_id = ? AND token = ?`。没有它会出两类事故：① 旧扫描收尾时的 `DELETE` 顺手删掉**新扫描刚写的行**，新扫描读到「行不见了」误判成被放弃而中止；② `waitWhilePaused` 读表时串进别次扫描的 `state`。`setScanState` 的 upsert 里 `token=0` 表示「调用方不知道归属」（如主进程重启后收到停止指令），此时保留库里的原 token —— 抹成 0 会让正在跑的扫描后续找不到自己的行。
    - **停止指令的「早到」窗口**：用户在派活后、子进程还没跑起 `runScan` 的那一小段里点了停止，此时子进程的 `running` Map 里还没有这个任务，IPC 的 stop 会被丢弃；库表通路此时也已被主进程写好（`state=cancelled`），子进程进 `runScan` 第一次检查点读到就会收工。子进程仍保留 `pendingStops` 集合兜底（主进程可能拿不到连接而只发了 IPC）。
    - **`readPendingScanTasks` 过滤 `state='cancelled'`**：用户明确放弃过的任务不该在重启后被 `/tasks/pending` 复活。
    - **「读到 paused 必须同时置本地标志」**（`waitWhilePaused` 里）：查库按 `STATE_CHECK_INTERVAL = 300ms` 节流，所以读到 `paused` 醒来后那一次调用会因「距上次查库不足 300ms」跳过查库，直接走到下面的 `if (task.paused)` —— 若本地标志还是 false 就会**放行**，把「暂停」变成每 200ms 漏放一个文件（库表明明写着 paused，扫描却一直往前推）。这不是理论风险：用户点暂停时子进程可能还没注册 `runScan`，那条 IPC pause 会被丢弃、本地标志压根没被置上。故读到 paused 时 `task.paused = true`，读到 running 时置回 false（本地可以没有 IPC，库表是唯一真源）。
    - **IPC 协议**：下行 `start` / `stop` / `pause` / `resume` / `demand` / `shutdown`，上行 `ready` / `progress` / `thumbs` / `demand-done` / `done` / `error`。`thumbs` 顺带承担「预热主进程缩略图索引」的职责。
  - **续扫时补缺缩略图**：断点之前的文件里可能有「索引已建但缩略图生成失败」的（`genThumb` 失败时只写索引、不写 `thumb_path`）。续扫跳过它们就会永远缺图，故续扫时回头把缺缩略图的补上（正常的跳过，不重扫）。
  - **续扫不清空索引**：`fullScan` 从头扫才 `DELETE FROM album_photos`，续扫保留已扫好的部分（否则白扫）。
  - **续扫不误删索引**：增量扫描末尾的「清理已删除文件」靠 `foundPaths`（本次清单的全量路径集合）判断，续扫时 `foundPaths` 必须填**全部**清单文件，不能只填处理过的那半段 —— 否则前半段会被误判为「已删除」而清掉索引。
  - **收集阶段被中断不得兜成空清单**：`collectMediaFiles` 返回 `null` 表示被中断。曾经写成 `(await collectMediaFiles(...)) || []` 把它兜成空数组 —— 空清单会让末尾的「清理已删除文件」把索引里**所有**行都判为「磁盘上已不存在」，整个相册的索引被删光（数据丢失）。现改为 `if (collected === null) return;`（增量：不改索引、保留断点，等用户续扫；全量：直接放弃本轮）。
  - **`INSERT OR IGNORE` 冲突时 `lastInsertRowid` 不可靠**：`changes===0` 时它是上一次插入的残留值，直接拿来写缩略图会写到别的行上（续扫时前半段已插入过，必然走这条分支）。故冲突时改为回查真实 id。
  - **接口**：`GET /api/album/tasks/pending` 读库表返回上次遗留的未完成任务（与 `GET /api/album/tasks` 读 `scanWorker.active` 互补：重启后内存空了但库里还留着断点）；`POST /api/album/tasks/resume`（body `{albumIds}`，不传则续全部）按断点续跑（`scanWorker.dispatchResume`，同样为每个任务换新 token 并保留 `done_path`），已在跑的相册会跳过，相册已删/是虚拟相册的会清掉断点不再续。
  - **不在后端启动时自动续扫**：那会跟软件启动抢 CPU/IO。恢复由**前端**在完全启动后触发（见 `composables/useAlbumTaskResume.js`：占位页移除 → 小组件就绪 → **延迟 4 秒** → 查 `/tasks/pending` → 弹顶部通知条 → 调 `/tasks/resume`）。

### 4.8 撤销（undo 路由）

- 存储：`undo_history` 表（key/type/label/payload/dir/ts，`dir=1` 为 undo 侧、`0` 为 redo 侧），跨重启可继续撤销；每 key 上限 `MAX_PER_KEY = 50`。
- 执行器 `executors`：以 `type` 注册 `validate/undo/redo/describe`，覆盖单格编辑、行增删改、网格整块覆盖（seat/schedule/duty）、相册排序、分组结构快照、照片回收站、相册增删、照片索引移动（`album_photo_move`）。表名受 `ALLOWED_TABLES` 白名单与 `GRID_SOURCES` 固定表约束，杜绝注入。
- 流程：`pushRecord` 新增记录并让该 key 的 redo 侧失效、裁剪最旧记录；`flip(id, fromDir, toDir, mode)` 校验方向后 `await` 执行对应动作、切换 `dir`、按当前方向生成展示文案。
- 接口：`GET /`（按 key 分组）、`POST /`（新增记录）、`POST /table/:key/undo|redo`（供快捷键撤销/重做最近一条）、`POST /:id/undo|redo`、`DELETE /:id`、`DELETE /?key=all|key`。
- 与相册的联动：照片删除的 undo/redo 通过 `albumOps` 搬移文件并还原 `album_photos` 索引；相册的 undo/redo 通过 `routes/album.js` 导出的 `cancelScan`/`startScan` 控制后台扫描；移动照片索引（`album_photo_move`）的 undo/redo 只重建 `album_photos` 行——按 `file_path` 删目标侧新增行、按原 id 还原被搬走的来源行，不碰磁盘文件。

## 五、注意事项与约定

- 硬性密钥约束：`DB_MASTER_KEY` 缺失时 `dbManager` 加载即抛错；`.env` 已不承载明文密钥，由 Electron 主进程首启现场生成并经 safeStorage/DPAPI 持久化后随 fork 注入。
- 只监听回环地址：服务仅绑定 `127.0.0.1`；Host 头非 `localhost/127.0.0.1/[::1]` 一律 403。
- 懒加载与重依赖：`app.js` 顶层只加载登录必需路由，其余路由与 sharp/pdf-parse 等重依赖延后加载；真实渲染请在改动后确认 `setImmediate` 注册顺序仍能命中。
- 已删除的历史死代码：`routes/students.js`、`routes/feeRecords.js` 曾是 `services/tableService.js` 的手写副本、且**从未被任何文件 require**（学生表、班费表实际由 `routes/dynamicTable.js` 工厂生成并挂载），已作为死代码删除。修改这两类接口请以 `dynamicTable.js` + `services/tableService.js` + `app.js` 挂载配置为准。
- 周历史快照的公共实现：`routes/historyRoutes.js` 抽取了「列表 / 单周 / 保存 / 删除」四组同构路由，供 `duty.js`、`schedule.js` 复用（差异为历史表名、`includeId` 与快照字段的解析/序列化，通过参数注入）。`seats.js` 的快照**不复用**该工厂——其 `seat_history` 表结构不同（除 week_start/settings 外还有 mode/rows/cols/seats/aisle_cols/groups_config 等列），行为差异较大，保持独立。
- 多库数据隔离：业务路由依赖 `auth` 中间件绑定库；新增路由务必挂到 `auth(['teacher'])` 之后，否则 `db` Proxy 会因未绑定库而抛错。
- 列名/表名注入防护：动态列操作统一走 `tableService` 的正则白名单；直接拼 SQL 的路由（如 undo、各网格路由）均对表名走固定集合或 `PRAGMA table_info` 校验，改动时须保持该约束。
- 共享目录：`uploads/`、相册缩略图 / 回收站为多账号共享资源，删除账号（`deleteTeacher`）不清理它们。
- 备份包 v2 语义：`encrypted` 标记备份来源是否为加密库；`key`（明文库钥匙）/`wrappedByPassword`/`wrappedByMnemonic` 三选一，`dbManager.decryptBundleKey` 按「明文 key 优先 → 密码 → 助记词」顺序尝试解锁。
- `cert.pem` / `key.pem` 的实际用途在当前后端代码中未出现（待确认）。
