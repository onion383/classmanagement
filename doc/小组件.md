# 班集 · 小组件文档

本文覆盖「班集」的两个独立窗口入口子系统——**工具箱浮窗**（`widget`）与**桌面小组件**（`desktop-widget`），跨渲染层（`student-frontend/src/subwindows/widget`、`src/desktop-widget`）与主进程（`electron/main.widget.js`）。

此前这部分内容附在前端文档的「浮窗与独立窗口」小节，现独立成文；前端其余内容见 [前端/前端总览.md](./前端/前端总览.md) 与 [前端/其他.md](./前端/其他.md)，主进程侧完整说明见 [主进程/主进程.md](./主进程/主进程.md)。

## 一、构成

两者都是「独立 HTML 入口 + 独立顶层组件」的独立渲染窗口，由主进程单独创建：

| 子系统 | HTML 入口 | 入口 JS | 顶层组件 | 用途 |
| --- | --- | --- | --- | --- |
| 工具箱浮窗 | `widget.html` | `src/subwindows/widget/main.js` | `src/subwindows/widget/WidgetApp.vue` | 悬浮工具箱：正/倒计时、点名、屏幕注释、一键截屏 |
| 桌面小组件 | `desktop-widget.html` | `src/subwindows/desktop-widget/main.js` | `src/subwindows/desktop-widget/DesktopWidget.vue` | 桌面常驻信息面板：时钟、倒计时、下节课、课程、值日与人数 |

两者均在 `vite.config.js` 的 `rollupOptions.input` 中登记；主进程 `electron/main.widget.js` 负责窗口创建与生命周期。

## 四、主进程侧（`electron/main.widget.js`）

窗口生命周期与 IPC 全部集中在 `electron/main.widget.js`（导出 `registerWidgetIpc`、`createWidgetWindow`、`hideWidgetWindow`、`showWidgetWindow`、`createDesktopWidgetWindow`、`getWidgetWindow`、`getDesktopWidgetWindow`、`setDesktopWidgetWindow`、`isDesktopEnabled`）。

**工具箱浮窗**：

- 窗口属性：`frame:false + transparent:true`、`alwaysOnTop`、`skipTaskbar`、不可缩放。
- 尺寸为「视觉内容 + 2×`WIDGET_SHADOW_MARGIN`(16px)」，用于绘制阴影。
- **会话级显隐采用「隐藏即 `destroy`」**（而非仅 `hide`），以释放整个渲染进程；重启用 `lastWidgetBounds` 复原位置。
- **菜单面板底部「退出工具箱」按钮**：与右键「关闭工具箱」同一动作（渲染层发 `widget-exit` → 主进程 `exitToolbox()`）。点击后先用项目已有组件 `ConfirmDialog` 二次确认「确认退出工具箱吗？下次启动需要在设置里重新启用。」——浮窗平时只有图标大小、塞不下弹窗，所以确认前先切全屏（`widget-fullscreen`），取消时 `widget-restore` 恢复到全屏前的尺寸与位置（菜单保持展开）。
- **右键菜单「关闭工具箱」**：关闭浮窗的同时把持久化开关 `toolboxEnabled` 一并置 false——主进程只负责隐藏窗口并通知主窗口（`from-main` 的 `toolbox-close-request`），由主窗口 GET 完整设置后整体 PUT 写回（后端是整体覆盖，只传 `toolboxEnabled` 会把两个保存路径清空）。因此设置页「是否启用工具箱」会同步变为关闭，下次启动也不再出现。设置页已去掉独立的「本次启用工具箱」开关：它只影响本次运行，与右键关闭的语义重复；现在「是否启用工具箱」本身即时生效（`widget-set-session-visible`）。

**桌面小组件（独立进程）**：

- 宽 320、高度约屏幕 95%，无边框 + 亚克力（`transparent:false`）、不置顶、不可缩放。
- **窗口跑在独立的 Electron 进程里**：入口 `electron/desktop-widget-host.js`，生命周期由 `electron/main/main.desktop-widget-process.js`（spawn / 停止 / 退出监控）与 `main.widget.js`（按启用状态调用）管理。
- **为什么要独立进程**：组件要挂在桌面层（见下），而 **Explorer 重启会销毁 `Progman`、级联销毁挂在其下的子窗口**，导致挂载方 Electron **原生崩溃**——实测整个应用瞬间消失（无 JS 异常、无 dmp；同一时刻普通顶层窗口完全无感）。隔离后崩溃只影响这个子进程：主进程检测到它退出，延迟 1.2s 自动重建（每分钟最多 6 次，避免崩溃循环），组件自己回来，主应用不受影响。
- **入口分流**：`electron/main/main.js` 最顶部检测 `--desktop-widget-host`，命中后直接 `require('../desktop-widget-host')` 并 `return`，不再执行单实例锁 / 后端 / 主窗口逻辑。
- **状态继承**：主进程 spawn 时把 `app.getPath('userData')` 通过环境变量 `DW_USER_DATA` 传给 host，host 在 ready 前 `app.setPath('userData', …)`，两边共用同一个 Chromium profile，因此 `app://local` origin 下的 localStorage（token、主题、玻璃/日夜设置）自动继承，渲染层无需改动；`get-main-token` 在 host 里直接回 `null`，渲染层随即回退 localStorage。**开发模式必须显式传**：子进程是以「脚本路径 + 参数」拉起的，Electron 找不到 `package.json`、`app.getName()` 回退成 `Electron`，不传就会落到 `Roaming\Electron` 这个另一个 profile 上（实测踩过）。
- **「桌面组件关闭最底层（提升稳定性）」**：设置页「桌面小组件设置」里的第二个开关。勾选后主进程给 host 传 `--no-desktop-layer`，组件按普通顶层窗口创建——完全不碰 `Progman`，绝对稳定，代价是会盖住其他窗口、点击可能被抬到最前。层级在窗口创建时决定，所以切换时会自动重启组件子进程（`setDesktopLayerEnabled` → `restartHost`）。真实状态持久化在 `userData/desktop-widget-state.json`，设置页用 `get-desktop-layer-state` 同步，保证界面与实际层级一致。
- **启动即崩 → 自动降级**：子进程起来不到 8 秒就退出，记一次「启动即崩」；连续 3 次自动关闭桌面层并持久化（`autoDisabled` 标记），设置页会显示「上次因连续崩溃已被自动关闭」。这样即使某个环境（安全软件拦截跨进程 SetParent、系统策略、远程桌面）下桌面层完全不可用，用户也不需要在崩溃循环里去点开关。Explorer 重启属于「跑了很久才崩」，不计入，避免正常场景被误降级。
- **常驻桌面最底层（Windows）**：host 进程用 koffi 调 `SetParent` 挂到桌面壳 `Progman` 之下，成为「桌面层子窗口」，再用 `SetWindowPos(HWND_TOP)` 提到桌面层内部 z 序顶端（否则会落在 `SHELLDLL_DefView`/`SysListView32` 之下，看得见但点击全被吃掉）。效果：被任何应用窗口盖住、点击不会被抬到前台、Alt+Tab 不出现、`Win+D` 也不隐藏，但仍可点击。
- **必须同时改成真正的子窗口（`WS_CHILD`、去掉 `WS_POPUP`）**：只 `SetParent` 不改样式时，窗口在系统眼里仍是顶层窗口，点击会先走一遍「激活窗口」流程；而桌面子窗口永远无法成为前台窗口，这次激活会把点击吞掉——表现为「组件看得见、`PostMessage` 能进页面，但真实鼠标点不动、拖不动」。`WS_EX_NOACTIVATE` 试过无效（Chromium 对 `WM_MOUSEACTIVATE` 仍回 `MA_ACTIVATE`）。
- **拖动改为自实现**：挂载后 `-webkit-app-region: drag` 立即失效（系统把 `SC_MOVE` 转发给父窗 Progman），改由渲染层 `pointerdown/pointermove` 上报 `screenX/screenY`，host 进程 `SetWindowPos` 搬窗口（`desktop-widget-drag-start/move/end`，在 host 进程内处理）。子窗口坐标是「父客户区物理像素」，一律经 `desktop-layer.getRect/moveWindow` 读写，不与 Electron `setBounds` 的 DIP 口径混用，否则会漂移。
- **降级**：非 Windows / koffi 不可用 / `SetParent` 报错时自动恢复样式 + `SetParent(hwnd, 0)` 解挂，退回普通顶层窗口（可点可拖，但会盖住别的窗口）；总开关是 `main.desktop-layer.js` 顶部的 `DESKTOP_LAYER_ENABLED`。
- **启动时序**：窗口以 `show:false` 创建，先 `attach` 挂到桌面层、再 `showInactive()` 上屏，最后才 `loadURL`。顺序不能反——若以 `show:true` 创建，窗口会先以普通顶层窗口身份出现在最前面「闪一下」，然后再下沉到桌面层。`showInactive` 同时保证不抢用户当前窗口的焦点。
- **兼容**：`main.widget.js` 的 `getDesktopWidgetWindow()` 现在返回伪窗口对象（`isDestroyed`/`close`/`destroy`/`webContents:null`），托盘「关闭主窗口和桌面组件」、性能面板的重启/内存列表等既有调用方无需改动；主动 `stop()` 的退出不会被自动重建（`onExit` 用 `child !== proc` 区分主动停止与意外崩溃）。
- 遗留：挂载后窗口不能再走 `setBounds/setAlwaysOnTop`；`backgroundMaterial:'acrylic'` 对 Progman 子窗口的观感待人工确认。

**主要 IPC 通道**（均需在 [preload.js](../electron/preload.js) 白名单登记）：

- `on`：`widgets-ready`、`desktop-widget-enabled`、`desktop-widget-desktop-layer`、`desktop-widget-drag-start/move/end`、`widget-resize`、`widget-move-to`、`widget-center`、`widget-restore-position`、`widget-fullscreen`、`widget-restore`、`widget-set-ignore-mouse`、`widget-set-visible`、`widget-drag-start/move/end`、`widget-context-menu`、`widget-set-session-visible`、`to-widget`、`to-main`
- `handle`：`get-session-widget-visible`、`get-main-token`、`get-desktop-layer-state`

## 五、数据接口

| 接口 | 用途 |
| --- | --- |
| `GET / PUT /api/widget-settings` | 工具箱启用配置、常用软件列表、首页班级信息（另有 `GET/PUT /apps`、`GET/PUT /class-info`） |

## 六、约定与注意

- **IPC 白名单**：新增小组件相关通道必须同步加入 `electron/preload.js` 的白名单，否则前端调用会被静默拒绝或 `Promise.reject`。
- **主题一致性**：两个入口都先在 `main.js` 中 `applyTheme()`、再挂载顶层组件，保证浮窗/桌组件外观跟随当前主题。
- **token 来源差异**：工具箱浮窗走常规登录态；桌面小组件因无登录界面，token 通过 IPC `get-main-token` 向主进程索取（回退 `localStorage`）。
- **多窗口并存**：工具箱浮窗与桌面小组件可同时存在，但同一时刻各自至多一个实例；重建前需先销毁旧窗口。
