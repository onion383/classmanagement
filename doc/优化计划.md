本文是「**待办**优化计划」，与 [优化文档.md](./优化文档.md)（记录**已实施**的优化）互补：

- 本文：代码质量层面的**待启动**优化项，按优先级分级，供逐条「启动优化」后执行。

## 流程约定（沿用 problem.md）

- 每条优化需用户**明确启动**后才执行；启动后在对应条目追加 `正在优化`。
- 修改完成后追加 `已尝试优化`；用户测试无误后自行追加 `已确认优化`，该项才算闭环。
- 曾被验证依旧存在残留问题的，**不在子项追加「已尝试修复」标记**，待用户确认后再标记。
- 优先「小步迭代」：第一阶段仅做纯代码搬运、不改逻辑，确认无回归后再做后续清理。
- 结构类改动优先保证**行为一致**（启动耗时、交互观感不变），零视觉改动。

## B. 一致性与去重

### B1. 主题样式 token 化

- **现状**：4 套主题靠全局 CSS 覆盖（[theme-glass.css](../student-frontend/src/styles/theme-glass.css) 1068 行、[theme-night.css](../student-frontend/src/styles/theme-night.css) 737 行、[theme-glass2.css](../student-frontend/src/styles/theme-glass2.css) 609 行等），色值/圆角/间距散落在各大文件内。
- **问题**：视觉微调时改动面大、易遗漏；同一语义色在多份主题文件里重复定义。
- **方案**：抽象 design token（颜色 / 圆角 / 间距 / 阴影），各主题只覆盖 token 变量；逐步迁移，不改视觉。
- **风险**：**严禁改变现有观感**（用户明确要求保留既有视觉效果），迁移需逐屏比对。
- **本轮做法（第一刀）**：先收敛重复率最高的「玻璃层白色/黑色透明度」——同一字面值在主题文件里重复 10–21 次。在 [theme-base.css](../student-frontend/src/styles/theme-base.css) 的 `:root` 增加 `--alpha-white-06/08/10/12/15/30`、`--alpha-black-25` 七个 token（取值与原硬编码逐字一致），再把 [theme-glass.css](../student-frontend/src/styles/theme-glass.css)（62 处）、[theme-night.css](../student-frontend/src/styles/theme-night.css)（44 处）、[theme-glass2.css](../student-frontend/src/styles/theme-glass2.css)（2 处）共 **108 处** `rgba()` 换成 `var(--alpha-*)`；替换数量与原有字面值逐档核对一致，**渲染值不变**。
- **后续**：其余 rgba/hex（主题文件里还有 200+ 处）按「同一语义 → 同一 token」逐主题迁移；`.vue` 里的硬编码颜色本轮未动。
- **状态**：部分完成（token 层 + 玻璃透明度已收敛；其余色值待逐屏迁移）

### B2. 弹窗/对话框公共模式抽取

## C. 工程健壮性

### C1. 补关键路径测试

- **现状**：仅 `testjs/` 几个探针脚本（[inp-probe.mjs](../testjs/inp-probe.mjs)、[ocr-probe.mjs](../testjs/ocr-probe.mjs)），**无单元/集成测试**。

- **方案**：优先为「纯逻辑、无 UI、高风险」模块补最小单元测试（如 `utils/sql.js` 的 SQL 拼装、`services/businessRules.js` 的业务校验、`services/sanitize.js` 的字段清洗、恢复密钥 normalize）。不追求高覆盖率，**只覆盖改坏代价高的地方**。
- **注意**：避免引入重的测试框架拖慢构建；按需最小化。
- **本轮做法**：用 Node 内置 `node:test`（零新依赖），新增 `testjs/units/`：
  - `recoveryKey.test.js`：`normalizePhrase`（只留汉字）/ `formatPhrase`（序号格式）/ `deriveRestoreHash`（稳定 + 64 位 hex + 不同短语不同值）/ `safeEqualHash`（仅相等字符串为真、非字符串为假）/ `pickPhrase`（12 个汉字）。
